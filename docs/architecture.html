Project architecture

How one request becomes reviewed code.

The project is a controlled workflow for software changes. BB shows the people doing the work. LangGraph controls the order. Python applies the rules. Git holds the actual files.

01 / System

The whole system on one page

A request enters through BB. The factory engine starts a LangGraph run. Each node either asks a specialist to think, lets Python perform a fixed check, or writes a record.

BB makes work visible

The parent task and three specialist threads can be inspected separately.

LangGraph controls sequence

Agents do not choose the route. Fixed Python rules choose it from saved state.

Git is the source of truth

The factory checks real file changes, not only what a Builder claims it changed.

02 / LangGraph

Nodes are jobs. Edges are decisions.

The graph is not an AI agent. It is a fixed route through small Python functions. State passes from one node to the next, and checkpoints remember the last completed point.

State = the run’s shared note

It contains the request, file paths, counters, test result, review result, status, and current error.

Checkpoint = a saved place

LangGraph stores progress in SQLite. resume continues the same graph thread.

Conditional edge = a rule

For example: if tests pass, go to Review; otherwise use Repair only while its budget remains.

03 / Worktree

One shared workbench, with strict permissions

A Git worktree is one working copy of the target repository. Every specialist sees the same files, but only the Builder is allowed to change ordinary project files.

Planner
Reads the clean starting point

The factory takes a Git snapshot. Any edit is restored, including changes to the index.

Starts clean

Bootstrap refuses to begin if the repository already has changed or untracked files.

Protected paths

Policy can protect files such as .factory/factory.yaml, .bb/, and deployment workflows.

Ends inspectable

The factory leaves the resulting worktree in place. It does not commit or publish it.

Important distinction: the factory coordinates work inside a target project’s worktree. It does not create a separate copy for each specialist; the permission policy makes one shared copy safe.
04 / Memory

Human records beside machine memory

The run produces readable files for inspection and durable database records for recovery. Both use the same run ID.

Inside the target worktree

.factory/runs/<run-id>/

Evidence a person can open and understand.

  • Original request and validated plan
  • Builder’s structured reports
  • Changed-file list from Git
  • Test logs and review attempts
  • Final report and run summary
Inside BB thread storage

factory/checkpoints.sqlite

Durable state the workflow uses to recover.

  • LangGraph checkpoints
  • Run status and ordered events
  • Planner, Builder, and Reviewer thread IDs
  • Spawn-intent ledger for crash recovery
  • Active child thread or test process
Agent outputMust match strict Pydantic JSON contracts. One correction attempt is allowed in the same thread.
Retry loopsRepair and revision limits are configuration values, so the graph cannot loop forever.
CancellationStatus is saved first; then the active BB child or whole test process group is stopped.
Publishing boundaryNo agent-proposed command is executed. Agent-created commits and ref changes are restored, full agent permissions are rejected, and direct shell or Git quality commands are invalid. Operator-reviewed quality programs remain a verification-only trust boundary.
